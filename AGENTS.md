# AGENTS.md — Autonomous Agent Governance, Git Automation & Contracts

> **Scope**: This document establishes the binding engineering standards, Conventional Commits policy, Pull Request (PR) automation protocols, Issue lifecycle contracts, and Git Worktree isolation rules for all AI agents and human contributors operating in Nereus 2.0.

---

## 1. Core Agent Invariants

1. **Strict Language Rule**: All code identifiers, comments, documentation, commit messages, PR descriptions, and issue discussions must be conducted in **100% idiomatic English**.
2. **Offline-First Verification**: Every change must pass offline test suites (`cargo test` or `StubLLMClient`) before any commit or push is initiated.
3. **No Direct Pushes to `main`**: The `main` branch is governed by repository rulesets and serves as the release gate. All changes must pass through feature branches and pull requests targeting `develop`.
4. **Zero Secret Leakage**: API tokens (e.g., `OPENROUTER_API_KEY`, `NEREUS_API_KEY`) must never be written to files, commits, or logs.

---

## 2. Conventional Commits Specification

All commit messages generated by agents or developers must strictly adhere to the [Conventional Commits v1.0.0](https://www.conventionalcommits.org/) specification.

### 2.1. Commit Message Structure

```text
<type>(<scope>): <short summary in imperative mood>

[optional body explaining WHY this change was made and WHAT it achieves]

[optional footer(s): issue references, co-author attribution, BREAKING CHANGE]
```

### 2.2. Allowed Commit Types

| Type | Purpose | Example |
| :--- | :--- | :--- |
| `feat` | New feature, agent capability, or user-facing addition | `feat(nereus-sandbox): implement wasmtime runner` |
| `fix` | Bug fix or state machine transition correction | `fix(nereus-engine): clamp passing threshold <= 85.0` |
| `refactor` | Code restructuring without behavioral alterations | `refactor(nereus-core): extract FSM state to enum module` |
| `perf` | Performance improvement or latency reduction | `perf(nereus-storage): enable sqlite WAL mode` |
| `test` | Adding or updating offline unit/integration tests | `test(nereus-engine): add socratic retry loop assertions` |
| `docs` | Documentation additions or corrections | `docs(architecture): specify 3-tier hot-switching` |
| `chore` | Build configuration, workspace scaffolding, dependencies | `chore(workspace): configure 9-crate virtual manifest` |

### 2.3. Scopes & Conventions

* **Scope** must correspond to the workspace crate or domain area:
  - `nereus-core`
  - `nereus-engine`
  - `nereus-agents`
  - `nereus-llm`
  - `nereus-sandbox`
  - `nereus-storage`
  - `nereus-tui`
  - `nereus-plugin`
  - `nereus-cli`
  - `workspace` / `deps`
* **Summary line**:
  - Maximum 72 characters.
  - Lowercase, imperative mood (e.g., "add", "implement", "fix", not "added" or "adds").
  - No trailing period (`.`).
* **Commit Body**:
  - Required for non-trivial features, architectural shifts, and bug fixes.
  - Explains the **motivation** (why) and the **implementation approach** (what).
* **Breaking Changes**:
  - Must include `BREAKING CHANGE:` in footer or `!` after type/scope (e.g., `feat(nereus-core)!: redesign StateMachineContext`).

## 3. Automated Pull Request (PR) Protocol

Agents opening pull requests must follow this deterministic protocol:

### 3.1. Branch Naming Convention

```text
<type>/<crate-or-scope>-<kebab-case-slug>
```
* Examples:
  - `feat/sandbox-wasmtime-runner`
  - `fix/engine-threshold-clamp`
  - `refactor/core-algebraic-state`
  - `chore/workspace-modular-scaffold`

### 3.2. PR Title & Description Template

The PR title must match the primary Conventional Commit format. The PR description must adhere to this structured template:

```markdown
## Summary
A concise 2-3 sentence overview of what this pull request introduces.

## Motivation & Architectural Context
- Why is this change necessary?
- Which milestone or architectural phase does this fulfill?

## Key Changes
- `crates/<crate>/src/...`: Description of modular changes.
- Crate-level API additions or trait implementations.

## Verification & Testing
- [x] Hermetic offline tests pass: `cargo test -p <crate>`
- [x] Code formatting verified: `cargo fmt --check`
- [x] Linter clean: `cargo clippy -p <crate> -- -D warnings`
- [x] Deterministic execution verified via `StubLLMClient`

## Invariants & Safety Check
- [x] Zero API tokens leaked or committed.
- [x] No breaking changes to `nereus-core` traits (or version bumped accordingly).
- [x] Worktree branch is cleanly rebased on `develop`.
```

### 3.3. Target Branches & Review Protocol

* All feature and bugfix PRs target **`develop`** (the integration lane).
* Only release promotion PRs target **`main`** (`develop -> main`).
* Releases on `main` require CI success (`lint-and-test`), admin review, and signed tags.

## 4. Automated Issue Protocol

When agents or contributors file issues in the repository:

### 4.1. Issue Types & Prefixes

* `[Feature]`: New architectural or subsystem capability.
* `[Bug]`: Deviation from specification or state machine deadlock.
* `[RFC]`: Architectural proposal requiring community or team consensus.
* `[Task]`: Granular engineering chore or refactoring task.

### 4.2. Required Structure

Every issue must specify:
1. **Context & Motivation**: Why this issue exists.
2. **Proposed Solution / Specification**: Code snippet or trait signature.
3. **Target Crate**: Which workspace crate(s) are affected.
4. **Acceptance Criteria (DoD)**: Verifiable bullet points that must be true for closure.

## 5. Git Worktree Isolation Workflow for Agents

To avoid compilation lock contention and allow parallel subagent development, agents must use `git worktree`:

```bash
# 1. Create an isolated worktree for a specific crate feature
git worktree add worktrees/sandbox-wasmtime feat/sandbox-wasmtime

# 2. Enter worktree and execute work
cd worktrees/sandbox-wasmtime

# 3. Verify crate independently
cargo test -p nereus-sandbox

# 4. Commit and push feature branch
git add .
git commit -m "feat(nereus-sandbox): integrate wasmtime in-memory runner"
git push -u origin feat/sandbox-wasmtime

# 5. Clean up worktree after PR merge
cd ../..
git worktree remove worktrees/sandbox-wasmtime
```

## 6. Local Kanban Board Integration

Agents must synchronize development state with the **Local Kanban Board** located at `.kanban/` on the local device:
* Before starting a task: Move the card from `1-ready` to `2-in-progress`.
* After implementing & verifying tests: Move card to `3-review` and link the PR branch.
* Upon merging: Move card to `4-done`.
* All local board files in `.kanban/` are strictly local to the device and gitignored.
